# Phase 5 — Observability, hardening, backups (+ Heatmap, PWA manifest)

> Working plan for Phase 5 (see `PROJECT-BRIEF.md` §11: *"Heatmap, OTel, PWA
> manifest, backups with a verified restore."*). Tracks stage status as work
> lands.

## Context

Phase 4 shipped the app to production with no logging/monitoring/backup
story beyond a hand-rolled `/api/health` endpoint and Docker's default
container logging. The brief's one-line Phase 5 scope bundles two very
different kinds of work: operational hardening (observability, backups —
the user's actual current priority, "learn the full lifecycle... harden the
app and the server") and product features (a completion heatmap, a PWA
manifest). ADR 0011 (`docs/decisions/0011-observability-backups.md`)
records the tool choices for the operational half: Grafana Cloud + Grafana
Alloy for metrics/logs/traces, OpenTelemetry .NET SDK for app
instrumentation, Sentry free tier for error tracking, `restic` → Backblaze
B2 for backups with a mandatory verified-restore drill, and a free external
uptime checker. Read that ADR before touching any stage below — it has the
full Rationale for each tool choice, not repeated here.

**Ordering:** hardening/observability stages first (this is the stated
priority and the more architecturally load-bearing half), product features
(Heatmap, PWA manifest) after. Each numbered stage is one reviewable diff;
stop after each for review — except human-owned account/access-provisioning
stages, which aren't diffs at all (same pattern as Phase 4's Stages 2/5).

---

## Stage A — Accounts & access provisioning (human-owned)

**Status: Not started.**

- Create a Grafana Cloud free-tier account/stack; generate an Alloy
  connection config (endpoint + API key) for metrics/logs/traces.
- Create a Sentry free-tier account/project (one for `api`, one for `web`,
  or a single project split by component — decide at implementation time);
  generate DSNs.
- Create a Backblaze B2 account, a bucket, and an application key scoped to
  that bucket only.
- Sign up for a free-tier uptime checker (UptimeRobot or Better Stack);
  point it at the production domain.
- Not a Claude Code implementation stage — credentials/config values feed
  into Stage B–D but aren't generated by writing code.

**Verify:** each account exists, each key/DSN/bucket is reachable (a trivial
test push/API call from a local shell), nothing yet wired into the app or
server.

---

## Stage B — Grafana Alloy: app telemetry + server-wide log collection

**Status: Not started.**

- Add OpenTelemetry .NET SDK to `api/Directory.Packages.props` +
  `api/Api/Api.csproj` (`OpenTelemetry.Extensions.Hosting`,
  `OpenTelemetry.Instrumentation.AspNetCore`, `.Instrumentation.Http`, an
  Npgsql instrumentation package); wire `UseOtlpExporter()` in
  `api/Api/Program.cs` targeting `localhost:4317`.
- Install Grafana Alloy on the host (outside `infrastructure/
  docker-compose.yml` — see ADR 0011's Rationale for why: it needs the
  Docker socket, host log files, and `journald` across the whole box, not
  just the Compose network, mirroring the host-level Caddy's placement from
  Phase 4 Stage 2).
- Alloy config scope (per ADR 0011): the API's OTLP export; `api`/`caddy`/
  `postgres` container logs (Docker log-collection component); host-level
  Caddy's access/error log; `fail2ban`; `ufw`; `unattended-upgrades`;
  `auth.log`/`sshd` via journald.
- Add a `log` block to `infrastructure/Caddyfile` (currently absent —
  compose-internal Caddy only emits default, uncustomized log output today).

**Verify:** traces/metrics/logs from a real request against production
appear in Grafana Cloud; each server-side log source (fail2ban, ufw,
unattended-upgrades, auth.log, host Caddy) shows up as its own labeled
stream, not just the app's own output.

## Stage C — Sentry: error tracking (api + web)

**Status: Not started.**

- Add the Sentry .NET SDK to `api`, wired for unhandled exceptions.
- Add the Sentry Angular SDK to `web`, wired for unhandled errors.
- DSNs sourced from Stage A, following the existing env-var-for-secrets
  pattern (`SEED_USER_PASSWORD`/`POSTGRES_PASSWORD` in `.env`) rather than
  hardcoding.

**Verify:** a deliberately thrown test exception in each of `api` and `web`
appears in the corresponding Sentry project.

---

## Stage D — Backups: `restic` → B2, with a verified restore

**Status: Not started.**

- `pg_dump` (logical dump, not raw volume files — see ADR 0011 Rationale)
  piped through `restic` to the B2 bucket from Stage A, on a systemd timer
  (not cron — see ADR 0011).
- **Mandatory, not optional:** actually run a `pg_restore` against a scratch
  database from a B2-fetched backup, and document the result — this is the
  gap Phase 4 explicitly deferred here rather than allowing an unverified
  cron job.

**Verify:** the systemd timer fires and produces a new snapshot in B2 on
schedule; a real restore drill against a scratch database succeeds and is
recorded (date + outcome) somewhere durable (this file, once done, or
`docs/existing-problems.md` if a gotcha turns up).

---

## Stage E — CSP header (closes an existing tracked gap)

**Status: Not started.**

- Set `optimization.styles.inlineCritical: false` in `web/angular.json` to
  stop Angular inlining critical CSS into `index.html` (the thing currently
  blocking a CSP), per `docs/existing-problems.md`'s existing entry on this.
- Add a `Content-Security-Policy` header to `infrastructure/Caddyfile`
  alongside the existing HSTS/`X-Content-Type-Options`/`Referrer-Policy`/
  `X-Frame-Options` headers.
- Remove the closed item from `docs/existing-problems.md` once done.

**Verify:** browser dev tools show no CSP violations on a full app
walkthrough (dashboard, challenges, login); response headers show the new
`Content-Security-Policy` value.

## Process notes for execution

- One scoped stage per turn, per project convention — do not batch multiple
  stages into a single implementation turn.
- Stage A is explicitly excluded from that loop: it's human-owned account/
  credential provisioning, not something to delegate to a Claude Code turn.
- Stages F and G (Heatmap, PWA manifest) need their own scoping/interview
  pass before they get the same stage-by-stage treatment as A–E — deferred
  on purpose, not an oversight.
